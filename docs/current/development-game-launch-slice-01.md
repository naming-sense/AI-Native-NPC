# 별도 Development Game 수집 연결 보충 설계

별도 Development Game 수집은 준비한 게임 빌드를 새 프로세스로 실행하고, 그 실행의 세션과 수집 파일을 연결하는 방식이다.

**이 문서는 현재 구현 범위를 설명한다.** 과거 공개 보관본에 있던 모든 상태의 연속 감시, source 전체 문자열 일치, 문서·RED/GREEN 선행 절차는 아래의 관리된 로컬 수집 방식으로 교체한다. 저장소 밖의 이전 설계 원본과 과거 실행 기록은 보존한다.

기능과 작업 단위는 [일반 플레이 수집 구현계획](scenario-collection-play-session-index-v1-implementation-plan.md)을 따른다. 빌드·시작 기록의 필드는 [Runtime 가져오기 계약 §§3.2–3.3](runtime-capture-import-v1-contract.md)을 따른다. AI는 코드를 작성한다. 빌드는 명시적으로 요청받은 범위에서 AI가 수행한다. 검토·테스트·실행 확인은 사용자 담당이다.

**사용자가 요청한 자동 수집은 같은 준비 빌드의 새 세션까지 완료했다.** 준비 20261103-07의 첫 세션은 두 회차의 판단 기록 2개를 저장했다. 같은 빌드의 두 번째 세션은 두 회차의 판단 기록 4개를 저장했다. 두 번째 실행의 정상 최종 저장과 일반 플레이 복귀를 확인했다. 이전 파일 20개와 준비 완료 기록은 바뀌지 않았다. 재사용 때 새 빌드·cook은 수행하지 않았다. 이 결과는 자동 입력 수집이며 사람 플레이나 모델 학습을 뜻하지 않는다.

## 1. 실행 대상과 운영 전제

- 기존 `NeuralGame`, Win64/x64/Development/Game을 사용한다.
- 기존 설치 엔진과 ABI를 유지한다.
- 수집에는 새 Game 프로세스를 사용한다. 기존 Editor나 `UnrealEditor.exe -game`으로 대신하지 않는다.
- 수집 프로세스에 Live Coding·hot reload를 적용하지 않는다.
- 코드 변경을 적용할 때는 수집을 종료하고 새 빌드로 새 세션을 시작한다.
- 빌드·cook·staging·수집 출력은 별도 작업 위치에 둔다. 원본 Content·Config·Saved와 기존 수집 파일은 덮어쓰지 않는다.

2026-11-03 사용자는 NPC 초기 방향만 바꾸는 맵 수정의 승인을 요청받은 적이 없다고 밝혔다. 기존 문서의 ‘사용자 승인 예외’ 표현을 철회한다. 과거 기록에는 NPC 초기 방향 변경과 저장이 남아 있지만 승인 근거로 취급하지 않는다. AI의 추가 수정은 중단했다. 현재 변경 사실과 원본 백업 위치는 [로컬 작업 인계](../history/local-development-handoff-2026-11-03.md)를 따른다. 이번 인계에서는 원본 맵을 추가 수정하거나 복구하지 않는다.

신뢰한 로컬 운영자·준비 도구·설치 엔진을 전제로 한다. 다른 개발 폴더의 편집이나 무관한 Editor 사용을 금지하지 않는다. 수집 프로세스에 변경을 적용하지 않는 것이 운영 규칙이다.

새 Target, 엔진 수정, ABI 우회, 관리자 실행, 원격 제어 bridge, Shipping은 추가하지 않는다.

## 2. 준비 도구와 입력

준비 도구는 기존 `play_session_launcher.py`, `play_session_native_io.py`, `play_session_game_plan.py`를 사용한다. 도구 소스는 로컬 작업 영역에 있으며 이 문서의 GitHub 게시와 별개다.

빌드 대상 해석기(planner)는 읽은 receipt·project/plugin descriptor·Target.cs·Build.cs를 입력으로 받는다. 해석기는 파일을 빌드하거나 게임을 실행하지 않는다. 준비와 실행은 launcher가 담당한다.

| 입력 | 사용할 정보 |
|---|---|
| Game receipt | target·platform·configuration·architecture·Game 유형·Launch·산출물 |
| `NeuralGame.uproject` | 현재 project와 runtime module 구성 |
| project-local plugin descriptor | Game 대상과 Editor 전용 대상의 구분 |
| Target.cs·Build.cs 원문 | 실제 빌드 입력의 보관과 식별 |
| 빌드·cook 기록 | 실제 호출·결과·실행물·선택 map 준비 |

현재 지원 범위는 하나의 논리 project module `NeuralGame`이 `Binaries/Win64/NeuralGame.exe`에 포함되는 형태다. 지원하지 않는 실제 module·target·ABI는 명시적으로 거부한다.

Target.cs·Build.cs의 주석·공백·statement 표기까지 과거 전체 문자열과 같아야 한다는 제약은 제거한다. source 원문을 기록하되 실제 receipt·빌드 정의·실행물을 근거로 지원 범위를 판단한다. 임의 C#를 해석하는 범용 분석기를 새로 만들지 않는다.

JSON 형식 오류·중복 key·범위 밖 값·잘못된 파일 경로·누락된 실행물의 처리는 유지한다. 실제 정보가 없으면 임의 값으로 정상 계획을 만들지 않는다.

## 3. 빌드와 cook

기존 강제 빌드·cook·staging 생산 경로를 재사용한다. 빌드 기록의 `build_mode="clean_or_forced_project_modules"`는 유지한다. incremental 성공을 강제 빌드로 표시하지 않는다.

준비 결과에는 실제 호출 인수·종료 결과·log·receipt·EXE, 빌드 전후 source snapshot과 수집 계약을 연결한다. 실패한 도구 호출은 실패로 남긴다. 실제 기록 없이 size·hash·성공 결과를 만들지 않는다.

빌드 기록은 C++ 코드와 Windows 실행 파일 리소스를 구분한다. Unreal이 생성한 여러 C++ 파일을 묶어 컴파일하는 입력도 지원한다. 준비 도구와 게임의 기록 읽기 코드에 같은 구분을 적용한다. 각 작업의 실제 입력·출력과 최종 링크 기록은 유지한다.

선택 map은 `/Game/AINativeNPC/Maps/L_AINativeNPC_MVP`다. 기존 dependency 기록과 cook/staging 경로를 사용한다. 설치 Engine 전체의 재현 가능성 증명이나 미지의 모든 동적 asset 추적을 새 필수 과제로 추가하지 않는다.

source snapshot은 준비한 빌드의 입력 기록이다. 원본 개발 폴더·설치 Engine·원본 Saved 전체를 세션 내내 잠그는 장치가 아니다. 준비 도구는 별도 작업 위치에 쓰고 원본에 쓰지 않는다.

같은 세션의 NewEpisode는 준비한 빌드를 계속 사용한다. 회차마다 빌드하지 않는다.

**기존 빌드로 다시 수집하는 기능은 코드 작성 인계를 받았다.** 처음 준비할 때는 빌드와 cook/staging을 수행한다. 완료한 뒤 준비 결과를 가리키는 기록을 마지막에 저장한다. 다음 실행에서는 그 기록을 읽어 빌드·cook·staging 없이 기존 게임을 켠다.

빌드 기록은 원래 준비 시점의 내용을 보존한다. 이번 수집의 실행 번호와 프로세스 시작 정보는 새로 만든다. 새 세션의 시작 기록과 로그는 별도 위치에 저장한다. 이전 준비 도구의 생존 객체가 없어도 저장된 기록으로 실행하도록 연결했다.

재사용할 자료가 없거나 기록과 다르면 오류를 반환한다. 자동 재빌드나 다른 실행물 선택은 수행하지 않는다. 빌드할 때 보관한 소스와 실행 설정을 사용한다. 원래 개발 폴더의 이후 변경을 과거 빌드에 적용한 것으로 표시하지 않는다.

게임과 플러그인의 누락된 헤더와 타입 선언을 보완한 뒤 원본 프로젝트의 Editor·Game 빌드가 성공했다. 기존 빌드 옵션은 유지했다. 2026-11-02에는 준비 08의 Editor·Game 빌드, cook·실행 자료 배치와 준비 완료 기록 발행까지 성공했다.

실패한 준비 폴더와 발행한 준비 완료 기록은 보존한다. 실행 중 발견한 오류를 수정한 C++ 코드는 새 작업 폴더에서 빌드한다. 완료 기록 없는 과거 결과는 자동 변환하지 않는다. 성공한 준비 폴더는 처음 만든 위치에 유지한다. 사람 입력 모드에서는 새 게임을 켠 뒤 수집 시작 명령을 입력한다.

## 4. 실제 실행물과 기존 기록 형식

기존 module descriptor는 `{module_name,base,path,size_bytes,sha256}`다. 현재 Game은 다음 관계를 사용한다.

- `module_name`: `NeuralGame`.
- `base`: `project_root`.
- `path`: `Binaries/Win64/NeuralGame.exe`.
- size·digest: 실제로 읽은 동일 실행 파일 bytes에서 얻는다.

빌드의 `module_artifacts`와 시작 기록의 `loaded_module_inventory`에 실제 EXE 관계를 기록한다. 같은 EXE를 임의의 여러 module 행으로 늘리지 않는다. 가장 최근 timestamp의 DLL을 대신 선택하지 않는다.

실제 process EXE와 준비 기록의 대응은 시작 시 확인한다. D3D·DML·TBB 등 일반 runtime DLL은 project module로 오분류하지 않는다. 이 DLL들의 정상적인 load/unload를 코드 패치로 간주하지 않는다.

`UnrealMCPEditor`는 Editor 전용이다. descriptor가 배포 기록에 있다는 사실과 Game에서 Editor module을 실행한다는 사실을 구분한다. Game에서 Editor MCP를 사용할 수 있다고 가정하지 않는다.

### 수집에 필요한 게임 자료

게임 자료의 의존 목록은 선택한 맵과 일반 실행에서 참조하는 자료를 연결한다. 준비 도구와 게임은 같은 기준으로 이 목록을 읽는다.

- 테스트 폴더와 명시적인 자동검사 전용 코드 안의 가상 자료 경로는 제외한다. 중첩 조건 안의 검사 코드도 제외한다. 일반 실행용 `else` 경로는 유지한다.
- 현재 수집은 고정 Utility 정책을 사용한다. 아직 없는 Neural 모델과 승인 자료의 기본 경로는 이 수집의 필수 자료가 아니다. 두 자료가 실제 source snapshot에 있으면 기존 cook·경로·내용 확인에 포함한다.
- cook이 만든 JSON 진단 파일은 전체 관측 목록에 남긴다. 설치된 Unreal의 실행 자료 배치 도구가 이 파일을 제외하므로 실행 폴더에 같은 파일이 있어야 한다고 요구하지 않는다. 실제 셰이더 코드와 게임 자료의 내용 대조는 유지한다.
- 편집기에서 따로 저장한 Actor·Object 파일은 원본 입력 목록에 보존한다. cook 과정에서 맵에 포함될 수 있으므로 각각을 별도 실행 파일로 만들었다고 가정하지 않는다. 선택한 맵의 실제 의존 목록과 cook 결과를 연결한다.
- 게임이 실행 중 만드는 설정·로그 폴더는 cook 입력 목록에서 제외한다. 준비 도구, 재사용 실행기와 게임이 같은 범위를 제외한다. 다른 cook 자료와 실행 자료 배치 목록의 대조는 유지한다. 정확한 제외 위치는 부록에 적는다.
- 전체 cook 목록에 들어 있는 자료의 이름은 형식과 실제 원본·배치 경로로 확인한다. 현재 Game이 사용하지 않는 플러그인 자료까지 Game에 등록하도록 요구하지 않는다. 실제로 읽은 자료의 cook 대응 확인은 유지한다.
- 그 밖의 누락된 필수 자료는 기존대로 거부한다. 시작 시 실제로 읽은 자료와 cook 결과의 연결도 유지한다.

이 구분은 Neural 정책 사용 승인이 아니다. 모델이 없으면 기존 `ResolvePolicyReady=false`를 유지한다. 가짜 모델이나 승인 자료를 만들지 않는다.

## 5. 시작과 세션 연결

1. launcher가 고정 package와 실제 Game 실행물을 선택한다.
2. 새 프로세스를 비활성 Live Coding 설정으로 실행한다. retained process handle에서 PID·OS 시작 식별값·실제 EXE를 얻는다.
3. RuntimeInputs가 package의 형식·digest·빌드·실행물 대응을 확인하고 읽은 값을 소유한다.
4. GameInstance owner와 준비된 입력을 연결한다. 먼저 도착한 쪽은 다른 쪽의 준비를 기다린다.
5. owner가 session ID와 시작 파일을 배타적으로 예약한다.
6. launcher가 그 세션과 이번 실행을 연결한 시작 기록을 보낸다.
7. owner가 World·NPC·플레이어 준비를 마친 뒤 Context/Lease를 발급한다.

기존 상속 pipe와 닫힌 메시지 형식을 재사용한다. run/session/owner/generation 불일치, 부모 프로세스 종료, EOF와 실제 통신 오류는 처리한다. 새로운 RPC나 외부 임의 경로 입력은 추가하지 않는다.

실행기는 프로세스 시작 뒤 초기 파일 확인 완료를 최대 60초 기다린다. 회차 준비 제한 10초와 기존 40ms 제한은 유지한다. 초기 확인이 끝난 뒤에 세션을 예약하고 수집을 시작한다.

세션·회차·오류 기록의 새 번호는 공통 UUIDv4 생성 함수를 사용한다. UUIDv4는 정해진 버전·형식으로 만드는 고유 번호다. 외부에서 받은 번호와 기존 파일의 번호는 바꾸지 않는다. 형식이 틀린 입력은 기존대로 거부한다.

화면을 사용하지 않는 자동 실행은 초기 확인 뒤 세션 예약을 최대 10초 기다린다. 시작 기록 전송 뒤 준비 완료 응답도 최대 10초 기다린다. 응답이 없으면 실행기는 오류를 반환한다. 사람의 시작 명령 대기에는 제한 시간을 적용하지 않는다. 이 오류 처리가 게임 창을 자동으로 강제 종료하지는 않는다.

### 수집 화면으로 시작하기 — 기본 실행 흐름 확인

수집 화면을 포함한 새 빌드에서는 실행기에 `--collection-ui`를 지정한다. 실행기는 실제 Game 인수 끝에 `-ANPCCollectionUI`를 추가한다. RuntimeInputs는 이 선택 인수 하나만 추가로 허용한다. 다른 인수와 실제 프로세스의 대조는 유지한다.

화면에서 시작 버튼을 기다리는 시간에는 자동 시작 제한을 적용하지 않는다. 시작 요청 뒤의 세션 연결·회차 준비·사건·저장 제한은 그대로 적용한다. 옵션이 없으면 기존 자동 실행을 유지한다. 준비 완료 기록의 입력 주체도 그대로 유지한다. 사람 입력용 실행에서는 직접 플레이 시작만 허용한다. 자동 입력용 실행에서는 자동 수집 시작만 허용한다.

화면은 기존 PlayerController에서 열고 닫는다. 맵이 바뀌면 이전 화면을 제거한다. 새 Controller는 진행 중인 회차의 입력을 가로채도록 화면을 자동으로 열지 않는다. 화면 모드로 연 실행의 최종 저장 뒤에는 새 일반 플레이 화면에서 결과를 보여 준다. 화면을 여는 동안에도 회차 시간은 흐른다.

새 화면의 Editor·Development Game 빌드와 실제 버튼 조작을 수행했다. 자동 시작·회차 대기·다음 회차·진행 중 중단·최종 목록 저장·같은 빌드 재사용을 확인했다. 시야 상실 시나리오의 시간 초과, 펼친 목록의 글자 대비와 일부 검사 실패가 남아 있다. [수집 화면 확인 기록](../history/collection-ui-verification-2026-11-03.md)에 범위를 구분했다. 이전 준비 20261103-07과 저장된 수집 파일은 보존했다.

시작 시 읽고 소유한 고정 metadata를 매 tick마다 파일에서 다시 열지 않는다. 세션 중에는 owner·World·Lease·통신·실제 저장의 현재성을 확인한다. World 전환 시에는 새 World의 지원 map과 실제 준비 상태를 확인한다.

## 6. Live Coding과 hot reload

### 비활성 운영

실제 launcher는 지원하는 비활성 실행 인수를 사용한다. 이미 로드된 Live Coding API가 있으면 비활성화와 알려진 상태 확인에 사용한다. 조회를 위해 모듈을 새로 로드하지 않는다.

명백한 활성화·컴파일·패치 사실은 시작 거부 또는 진행 중 세션 실패 사유다. 단순 helper 시작은 패치 적용 사실이 아니다.

다음 조건은 시작을 막지 않는다.

- Live Coding 모듈이나 상태 조회 API가 없다.
- public API가 내부 `Starting`을 구분하지 못한다.
- tick 사이 모든 상태 변화를 관측할 수 없다.
- 무관한 DLL이 로드되거나 해제된다.
- 별도 개발 폴더나 무관한 설치 엔진 파일이 바뀐다.

### 기록의 의미

`live_coding_state="disabled"`와 `hot_reload_state="disabled"`는 실제 비활성 실행 설정과 해당 기능을 사용하지 않는 운영 규칙을 뜻한다. 누락 없는 연속 감시 인증을 뜻하지 않는다.

실제 실행 인수·얻은 상태 관측·운영 전제는 기존 `launch_argv`와 `loader_log`에 구분해 남긴다. 관측된 활성 상태와 모순되는 disabled 기록을 만들지 않는다. 기존 Schema에 가상의 증명 필드를 추가하지 않는다.

설치 엔진의 기본 ABI를 유지한다. `WITH_LIVE_CODING=0`이나 새로운 Target 설정으로 관측 문제를 우회하지 않는다. 기존 조건부 public-header include 경로는 유지한다.

## 7. 유지하는 오류 처리

다음은 정상적인 로컬 사용에서도 필요한 보호다.

- 잘못된 옵션·지원하지 않는 map·대상·플레이어 구성의 거부.
- 실제 EXE·빌드 기록·고정 입력·세션 연결의 불일치 처리.
- owner·World·회차 수명과 늦게 도착한 callback의 구분.
- 진행 중 timer·이동·dispatch의 종료 뒤 새 World 연결.
- 저장 경로 제한, 기존 파일 보존, 실제 쓰기·readback 실패 처리.
- 누적 예산·종료 예약·중복 ID와 중복 Stop 처리.
- 실제 사건이 없을 때 completed를 만들지 않는 규칙.
- 자동 입력·사람 입력·정답·학습 승인 구분.

기존 native FileStore와 wire의 제한을 단순화 명목으로 해제하지 않는다. 전체 개발 환경에 대한 적대적 변조 방어와 위의 데이터·수명 보호는 서로 다른 범위다.

## 8. 제외 범위와 인계

이번에는 전역 DLL 알림으로 모든 module 변화 추적, Source·Engine·Saved 전체의 세션 수명 잠금·변경 감시, 매 Capture의 전체 inventory 재검사, source 전체 문자열 일치, 엔진 내부 모든 상태 증명을 구현 선행 조건으로 사용하지 않는다.

적대적 로컬 실행자, crash 복구·동일 세션 재개, 범용 C# 분석과 추가 runtime module 구성은 후속 요구가 생기면 범위를 정한다.

현재 목표는 Start → 실제 입력과 관측 → NewEpisode → Stop → terminal/index 저장 → 일반 플레이 복귀다. 과도한 시작 거부·전역 감시·반복 inventory 검사·source 전체 문자열 제한의 코드 작성 정리는 마쳤다. 실제 launcher argv, 초기 package와 실행물 확인, 새 World 지원 map 확인은 유지했다. 사용자 요청에 따라 2026-11-02에 원본과 별도 준비 복사본의 Editor·Game 빌드를 수행했다. 앞선 준비 복사본에서는 cook과 실행 자료 배치도 성공했다. 함수 포인터 변환 경고는 남아 있다.

기존 빌드로 새 게임 프로세스를 실행하는 연결까지 코드 작성 인계를 받았다. 준비 완료 기록의 저장과 읽기, 새 실행·세션 구분, 실제 API와 명령줄 진입을 태스크 2에서 함께 작성했다. 빌드를 만든 실행 번호와 새 수집 실행 번호의 구분은 RuntimeInputs 소비 경로에도 적용했다.

### 이전 준비 과정

아래 미완료 상태는 각 준비 당시의 기록이다. 현재 수집 결과는 문서 앞의 최신 결과를 따른다.

준비 08과 09는 빌드·cook·완료 기록 발행을 마쳤다. 준비 08에서 발견한 실행 설정 폴더의 오분류는 준비 09에서 지나갔다. 준비 09의 Game은 맵을 연 뒤 자료 이름 검사에서 수집 연결을 거부했다. 전체 cook 목록의 미사용 플러그인 자료까지 현재 Game에 등록하도록 요구하는 조건을 수정했다. 실제 원본·cook·배치 경로와 로드한 자료의 대응은 유지했다. 초기 대기는 추가로 늘리지 않았다. 수정된 C++ 코드의 새 빌드와 실제 수집·같은 빌드 재실행 확인은 남아 있다.

준비 10의 Game은 초기 실행물·자료 확인을 마치고 세션 예약 단계에 도달했다. 새 세션 번호의 형식이 저장 규칙과 달라 수집 시작을 거부했다. 기존 번호 생성 함수를 세션·회차에도 연결했다. 자동 실행기가 시작 실패 뒤 무한 대기하던 처리도 보완했다. 수정본의 수집 시작·다음 회차·저장·재실행 확인은 남아 있다.

준비 11은 빌드·cook·완료 기록 발행과 세션 번호 형식 확인을 통과했다. 첫 세션 파일 저장에서 거부됐다. 실행기는 제한 시간 안에 오류를 반환했다. 저장 거부 지점과 연결 오류를 구분하는 로그를 추가했다. 차단된 자동 실행이 같은 오류를 반복 기록하던 처리도 수정했다. 저장 실패의 추가 원인과 실제 수집 성공은 아직 확인하지 않았다.

준비 12의 로그는 저장 전 검사 뒤 빈 저장 결과가 반환된 지점을 보여 준다. 저장 요청과 폴더 준비·쓰기·읽기 단계에도 실행 중 오류 기록을 추가했다. 저장 조건, 처리 순서와 기존 파일 보호는 유지했다. 추가 로그는 원인 진단용이며 저장 성공 증거가 아니다.

준비 14는 첫 세션 파일과 설정 저장, 실행기 연결을 마쳤다. 이후 새 게임 상태를 준비하다 시간 초과로 중단됐다. 같은 빌드의 재사용 실행도 같은 오류를 남겼다. 2026-11-03 진단 빌드에서는 준비 중 감각 입력이 NPC의 기억을 바꾸는 원인을 확인했다. 준비 동안 해당 입력 반영을 보류하고 회차 시작 뒤 실제 감각 입력을 처리하도록 수정했다. 준비 시간 제한과 초기 상태 조건은 유지했다. 수정본의 정상 플레이 수집과 최종 저장은 아직 미확인이다.

감각 입력 수정본은 회차 준비에 진입했다. 이후 플레이어 배치에서 실패했다. 실패 기록과 최종 목록 저장, 일반 플레이 복귀는 실제로 확인했다. 최종 목록에는 오류 기록 1개가 있으며 판단 기록은 0개다. 이 결과를 정상 수집 성공으로 분류하지 않는다. 배치의 실제 실패 단계를 구분하는 진단을 추가했다.

다음 진단 실행은 NPC 뒤 400cm 지점에서 바닥을 찾지 못해 실패했다. 실제 cook의 Actor 배치 기록도 해당 지점이 기존 바닥 밖임을 보여 준다. 실패 세션의 종료 파일과 최종 목록은 실제 읽기에서 확인했다. 원본 Content 보존 범위를 유지하므로 맵은 변경하지 않았다. 배치 수정 범위를 결정한 뒤 새 준비로 정상 수집을 이어가야 한다. 판단 기록, 다음 회차와 정상 수집 뒤 최종 저장은 아직 미확인이다.

## 부록. 재사용 진입점과 저장 위치

준비 완료 기록은 준비 작업 폴더 아래 `evidence/prepared-game-ready.json`이다. 명령줄 진입점은 `--reuse <준비폴더 또는 완료기록>`이다. Python 진입점은 `launch_reused_game(prepared=Path(...))`이다.

이번 실행의 입력은 준비 프로젝트의 `Saved/AINativeNPC/CollectionRuntime/<run_id>/`에 둔다. 실행 로그는 준비 작업 폴더의 `evidence/runs/<run_id>/`에 둔다. 원래 빌드 기록과 이전 수집 결과는 보존한다.

cook 목록에서 제외하는 실행 결과 폴더는 준비 프로젝트의 `Saved/Cooked/Windows/NeuralGame/Saved/`다. 게임이 이 폴더에 만든 설정·로그를 고정 빌드 입력으로 취급하지 않는다. `Saved/Cooked/Windows/`의 다른 자료와 전체 stage 목록은 기존대로 대조한다.

실행에는 Windows Python을 사용한다. 수집하는 동안 실행기를 유지한다. 준비·재사용 명령과 API 사용 예는 [일반 플레이 수집 구현계획의 부록 D](scenario-collection-play-session-index-v1-implementation-plan.md)에 정리했다. 이 사용법은 작성된 코드를 설명하며 실행 성공 증거는 아니다.

자동검사 전용 코드는 `#if WITH_DEV_AUTOMATION_TESTS` 분기를 뜻한다. 이 분기에서 나오는 가상 경로만 일반 실행 자료의 탐색에서 제외한다. 다른 조건식은 범용 전처리기로 해석하지 않는다.

위에서 말한 선택적 Neural 자료의 기본 경로는 `/Game/AINativeNPC/Policy/MD_AINativeNPCResolvePolicyV1`과 `/Game/AINativeNPC/Policy/DA_AINativeNPCResolveFreezeV1`이다. 이 예외는 현재 고정 Utility 수집 범위에 한정한다.
