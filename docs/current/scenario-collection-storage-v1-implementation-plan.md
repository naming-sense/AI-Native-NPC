# 수집 Capture 안전 저장·동일 이미지 검증 구현 계획 — Task2D

> **For Hermes:** `subagent-driven-development`로 문서/하네스를 확정한 뒤 lower와 실제 Host 연결을 따로 구현·검토한다. 이 문서 작성자는 파일 열람과 문서/pytest 하네스 작성만 수행한다. C++ 구현·명령 실행·build/test는 부모 담당이며 commit/push는 제외한다.

**Goal:** 수집 Capture의 기존 파일을 보존하면서 새 파일만 발행하고, 한 번 확보한 동일 byte image에서 검증 결과를 만든다.

**Tech Stack:** Unreal Engine 5.7 C++·Windows native file API·기존 Dataset/Host Automation·pytest 문서 일관성 하네스. 기존 ANPCCAP2/ANPCCMT2·Dataset v2·Schema·generated bytes를 유지한다.

## 3. 첫 구현 묶음: lower Store와 Dataset

- **D05**: lower 범위는 FileStore/Dataset/기존 DecisionRecordV2Tests뿐이다. legacy Writer/Reader signature·호출자·serialization 의미를 보존한다.

경로 기준은 `Source/NeuralGame/AINativeNPC/`다. 새 FileStore 두 파일과 기존 Dataset/시험 파일만 lower 묶음에 포함한다.

```text
Collection/AINativeNPCCollectionFileStore.h
Collection/AINativeNPCCollectionFileStore.cpp
Dataset/DecisionRecordV2.h
Dataset/DecisionRecordV2.cpp
Tests/DecisionRecordV2Tests.cpp
```

Store는 bounded byte I/O와 root/attempt ticket을 소유한다. ticket은 root physical identity, process sequence, 여섯 경로, stage, exact owned file identity를 보유하는 내부 소유 객체다. UUID/파일명 문자열이나 caller bool은 ticket 소유권을 대신하지 못한다. Dataset은 Record 직렬화·marker 결속·receipt 생성만 맡는다. JSON sidecar/diagnostic 작성, accepted ledger, owner/reset은 이 묶음에 넣지 않는다.

additive API는 다음 역할을 분리한다. 이름은 구현 시 이 파일군 안에서 확정하되 의미와 호출 순서를 바꾸지 않는다.

1. **root/attempt 확보:** 검증한 native root lease, immutable session/episode 값으로 process 번호와 capture 경로를 확보한다.
2. **pending 저장:** ExpectedRecord의 envelope bytes를 `final.pending.tmp`에 exclusive write하고 `final.pending`으로 non-replace publish한다.
3. **pending exact 검증:** 저장한 image를 실제 다시 읽어 expected bytes와 비교한다. writer의 메모리 buffer를 readback으로 세지 않는다.
4. **owned final promotion:** 같은 ticket의 pending만 final로 이동한다. 실제 호출자는 후속 Host의 `AtomicReserveAndStart`다.
5. **marker publish:** final image를 expected와 대조한 뒤 기존 marker helper로 생성하고 `.committed.tmp`→`.committed`로 발행한다.
6. **committed receipt:** final/marker의 새 readback image와 expected Record/current lease를 검증해 성공 전용 불변 결과를 반환한다.

새 public aggregate 성공 결과나 일반 path+digest receipt 생성자는 금지한다. Win32 타입은 cpp의 `PLATFORM_WINDOWS` 안에 숨긴다. 새 멤버는 `protected`의 `m` 접두어, const는 타입 뒤, 중괄호는 다음 줄에 둔다. legacy 스타일을 함께 재작성하지 않는다.

## 6. sequence와 두 종류의 경로 입력

- **D08**: process-wide checked uint64는 0을 발급하지 않는다. MAX_uint64는 마지막 유효 번호이며 이후 영구 실패한다. 실패 번호 재사용·World/Host/reset에 의한 초기화는 금지한다.
- **D09**: native root는 canonical local Windows absolute directory이고 artifact는 canonical POSIX relative path다. 두 입력 검사를 구분하며 trim/lowercase로 수선하지 않는다.
- **D10**: artifact의 absolute·drive·UNC·backslash·빈 component·dot/parent traversal·ADS·device name·alias를 거부한다.

final 상대 경로는 `captures/<session UUID>/<episode UUID>/<20digit>.anpccap2`이고 raw episode는 `scenario_capture_<session>_<episode>_<20digit>`다. 여기서 episode는 collection episode UUID다. session/episode는 기존 strict lowercase UUIDv4를 사용한다. `<20digit>`는 **20자리 unsigned decimal**이며 raw episode와 파일명에서 같은 값을 사용한다. DecisionId가 같아도 process sequence가 다르면 새 raw episode/sample/path가 생긴다.

allocator는 World/Host 밖 process 상태와 lock 또는 동등한 checked atomic 연산을 사용한다. 먼저 소진 여부를 확인하고 증가한다. 이미 발급한 번호는 collision/open/write/lease 실패에도 반환하지 않는다. 새 이름을 얻을 때까지 자동 재시도하는 복구 정책은 추가하지 않는다. MAX 경계 시험은 production과 같은 checked 연산을 쓰는 격리 dev state로 수행한다. live global allocator reset setter는 공개하지 않는다. process 재시작은 새 session UUID와 외부 중복 inventory를 요구하며 crash recovery로 해석하지 않는다.

**native root 입력:** trusted owner 또는 격리 dev fixture가 미리 선택한 실제 local Windows absolute directory다. drive-relative, UNC/network, device namespace, short-name/비정규 alias와 지원을 입증하지 못한 filesystem은 거부한다. store 내부의 검증된 native 변환만 허용하며 caller의 비정규 이름을 고쳐 수락하지 않는다. 원래 artifact 규칙의 absolute/drive 금지는 이 native root 자체를 거부하라는 의미가 아니다.

**artifact 입력:** 위 capture grammar의 canonical POSIX 상대 이름이다. root에 결합하기 전에 검증하고 Windows 표현으로 내부 변환한다. trailing dot/space, 대소문자 alias, 8.3 alias, ADS 등으로 같은 실제 파일을 두 이름으로 예약할 수 없어야 한다. lexical prefix 일치만으로 containment를 판단하지 않는다.

**기존 context root descriptor:** `IsFixtureRootDescriptor`는 기존 상대 descriptor 검증이다. 해당 immutable descriptor와 별도로 trusted native root binding을 보유하고 exact context에 결속한다. caller 문자열만으로 storage root authority를 새로 만들지 않는다. Task3 owner가 이 binding을 실제 발급하는 기능은 후속이다.

## 7. root 독점과 ancestor 수명

- **D11**: 실 filesystem root directory handle 독점과 cooperating process mutex를 함께 보유한다. 추가 persistent lock artifact는 만들지 않는다.
- **D12**: root 위 ancestor부터 destination parent까지 component별 directory handle을 no delete sharing으로 유지한다. reparse/alias/query failure는 reject한다.
- **D13**: 보장은 protected cooperating root에 한정한다. arbitrary malicious writer 방어·crash recovery·gameplay rollback은 범위 밖이며 unsupported는 fail closed다.

root lease는 다음 자원을 함께 보유한다.

- 실제 root directory의 독점 open handle. 동일 physical root의 두 번째 cooperating owner는 거부한다. root 자체는 exclusive share 정책을 사용하고 ancestor/descendant 보호 handle도 `FILE_SHARE_DELETE`를 허용하지 않는다. root 재검사는 이미 가진 handle에서 수행하여 자기 독점 open과 충돌하는 재개방을 피한다.
- 동일 physical root의 volume/file identity로 결속한 process 간 cooperating mutex와 process 내부 동시 attempt 직렬화. 단순 process-local mutex 하나로 다른 process까지 보호했다고 주장하지 않는다. mutex 획득·해제의 OS thread 소유와 lease lifetime을 일치시키고 abandoned/불명확 소유권은 fail closed 처리한다. named mutex는 kernel 수명 자원이며 lockfile 같은 영속 artifact를 남기지 않는다.
- volume root에서 시작해 trusted root 위 ancestor와 목적지 parent까지의 directory chain handle. 각 component를 reparse를 따라가기 전에 열어 directory/tag/identity를 확인한다. 목표 primitive는 `OPEN_EXISTING + FILE_FLAG_BACKUP_SEMANTICS + FILE_FLAG_OPEN_REPARSE_POINT`이며 query/access 실패는 absence로 바꾸지 않는다.

root 소유권은 World 수명보다 길고 모든 in-flight attempt/readback/cleanup보다 오래 유지한다. 실패나 terminal 때문에 게임 권한을 revoke해도 exact owned cleanup에 필요한 root guard는 cleanup 종료까지 pin한다. 이를 새 collection 성공 권한으로 해석하지 않는다. 두 cooperating writer가 동시에 시작하면 한 owner만 진행하고 나머지는 busy/reject한다. owner 해제 뒤 새로운 정상 owner의 실제 native control도 확인한다.

하위 directory가 필요하면 보호된 parent 아래 한 component씩 create/open/revalidate한다. recursive MakeDirectory 뒤 prefix 검사만 하는 경로는 허용하지 않는다. 생성한 directory의 inventory와 파일 attempt inventory는 구분하며 실패 후 root를 재귀 삭제하지 않는다. 각 stage 직전 held identity, path binding, current root lease, 예약 상태를 다시 검사한다. root 위 ancestor와 목적지 parent의 rename/replace 시도가 실제 OS에서 거부되는지 시험한다.

일반 UE `OpenWrite`/`FileExists`/일시적 normalized path 확인만으로 이 보장을 대체하지 않는다. 선행 조사가 확인한 UE5.7 `CREATE_ALWAYS`, file-only directory 누락, generic delete sharing 가능성을 피한다. Win32 include/access/share/identity/delete 조합의 실제 지원 여부는 부모가 해당 대상 volume에서 실행으로 확인해야 한다. 보장 없는 이름 기반 fallback을 추가하지 않는다.

## 8. 여섯 이름과 stage별 소유 상태

- **D14**: 여섯 예약 이름의 file·directory·reparse 충돌을 거부한다. final.tmp도 검사하며 stage별 exact owned identity만 허용한다.

`final`은 §6의 전체 `.anpccap2` 경로다. 아래 표의 owned는 현재 attempt가 실제 생성/이동한 physical identity와 같다는 뜻이다. 같은 이름의 존재만으로 owned라고 판단하지 않는다.

| stage | 허용 owned 이름 | 반드시 부재할 이름 |
|---|---|---|
| allocated | none | final,final.tmp,final.pending,final.pending.tmp,final.committed,final.committed.tmp |
| pending-temp | final.pending.tmp | final,final.tmp,final.pending,final.committed,final.committed.tmp |

| marker-temp | final,final.committed.tmp | final.tmp,final.pending,final.pending.tmp,final.committed |

## 9. native publication과 실패 cleanup

- **D15**: 각 stage에서 lease/reservations를 검사한다. CREATE_NEW → full write/flush/close → nonreplace MoveFileW 순서를 지킨다.
- **D16**: cleanup은 exact owned handle identity에 결속한다. foreign identity·충돌 sentinel·committed pair를 삭제하거나 truncate/replace하지 않는다.
- **D17**: post-start I/O failure는 과거 Commit/start counter rollback 금지다. raw final을 보존하고 receipt/verified를 새로 발행하지 않는다.

구현 순서는 다음과 같다.

1. current producer lease와 root/ancestor/reservation 상태를 확인한다. 유효한 입력·bound된 byte size가 준비된 뒤 exclusive temp 생성으로 진입한다.
2. `CreateFileW(...CREATE_NEW...)` 성공 handle에서 physical identity를 기록한다. open 실패는 소유권을 발급하지 않는다. file/directory 경쟁은 모두 실패다.
3. full write loop는 partial progress를 처리하고 zero-progress를 실패시킨다. `FlushFileBuffers`와 explicit close 결과까지 확인한다. write/flush/close 하나라도 실패하면 publish하지 않는다.
4. 닫힌 write handle 이후 재검증과 `MoveFileW`를 수행한다. 목적지 삭제, `Replace=true`, overwrite/copy fallback은 금지한다. native primitive 직전 경쟁은 실제 primitive가 거부해야 한다. 앞선 reservation 재검사에서만 실패한 결과를 last-moment race의 증거로 세지 않는다.
5. 성공한 이동의 source/destination identity·membership을 재확인하고 ticket을 전환한다. pending exact readback은 다음 Commit의 필수 장벽이다.
6. 실패 때 정확히 소유한 temp/pending만 retire한다. close 뒤 cleanup handle을 다시 확보해야 하면 열린 동일 handle에서 identity를 대조하고 그 handle에 delete disposition을 결속한다. `identity 확인→close→Delete(path)`는 허용하지 않는다.

cleanup identity를 확인할 수 없거나 cleanup 자체가 실패하면 residual을 보존·기록하고 실패를 반환한다. 이름이 외부 파일로 바뀌었으면 해당 파일을 삭제하지 않는다. owned-only cleanup은 초기 sentinel 전체 보존과 함께 검사한다. root guard 해제 전 cleanup을 마치며 committed pair는 이후 readback/sidecar 실패에서도 보존한다.

private Skill start **거절 전후**와 **성공 뒤**를 구분한다. start reject 뒤 uncommitted raw final은 기존 의미대로 owned quarantine/retire를 시도할 수 있다. 그 cleanup도 실패하면 marker 없는 residual raw final을 먼저 관찰한 뒤 committed Reader reject를 확인한다. 실제 start가 성공한 후 marker/receipt I/O 실패면 raw final은 보존한다. 실행 사실을 취소했다고 보고하거나 producer counters를 감소시키지 않는다.

flush/close 성공은 파일별 publication 조건이다. multi-file transaction, crash recovery, 전원 차단 내구성 또는 gameplay rollback의 증거로 확대하지 않는다. lower API는 failure/residual 정보를 반환하고 실제 Host의 session block/revoke 연결은 후속 Host 묶음에서 검증한다.

## 10. 동일 이미지 검증과 성공 전용 receipt

- **D18**: Dataset의 같은 cpp private BuildCaptureEnvelopeBytes/BuildCommittedMarkerBytes를 재사용한다. 새 parser·wire format·공개 serializer를 만들지 않는다.
- **D19**: committed-readback은 Capture 1회 + marker 1회다. 같은 immutable images로 exact expected bytes·marker·size/hash를 계산하며 legacy chain read와 hash용 재개방을 금지한다.
- **D20**: receipt는 Reader-only immutable result다. 실패 미발행·strong context lease pin·publication 직전 current lease 재검사를 요구한다. public path+bool/digest mint는 금지한다.
- **D21**: pending readback과 marker 생성 I/O는 별도 집계한다. invalid-first·mixed images·감지된 rebind는 재시도 읽기 없이 실패한다.

Reader의 필수 알고리즘은 다음과 같다.

1. expected Record는 값 복사하고 Snapshot은 기존 immutable 소유권을 유지한다. root/ticket 및 실제 `TSharedPtr<FAINativeNPCCollectionContext const>`, `TSharedPtr<FAINativeNPCCollectionLease const>`를 strong pin한다. current authority/lease 검사는 기존 Host binding을 관찰하는 경로에 결속한다.
2. `BuildCaptureEnvelopeBytes(ExpectedRecord)`로 expected 전체 envelope를 만든다. `ValidateReplay` 실패면 종료한다. 일부 identity/hash만 맞추는 검증은 금지한다.
3. final Capture를 한 번 열어 bounded complete image를 확보하고 marker도 한 번 열어 complete image를 확보한다. 실제 read handle은 write/delete sharing을 허용하지 않고 image 확보·검증·최종 identity 확인 동안 유지한다. 동일 handle 안의 chunk read는 재개방으로 세지 않는다.
4. Capture image와 expected 전체 bytes를 exact 비교한다. 같은 `InputContentHash/SampleId`를 유지하면서 metadata만 바꾼 유효 B도 이 비교로 거부한다.
5. 읽은 Capture image를 `BuildCommittedMarkerBytes`에 전달하고 읽은 marker image와 exact 비교한다. size/trailing/marker binding 불일치를 거부한다.
6. 동일 Capture/marker image에서 각각 size와 SHA-256을 산출한다. root-relative path, expected episode/decision/input/sample identity, metadata 값 복사, context/lease identity와 묶는다. 읽기 이후 disk를 hash/parse 목적으로 재개방하지 않는다.
7. physical identity/예약 상태/current producer lease를 다시 확인한 뒤 Reader만 receipt를 생성한다. 호출 중 callback/rebind/revoke가 있었으면 실패한다. receipt 안의 strong pins는 그 결과의 수명을 유지하며 향후 bridge도 소비 시 current lease를 다시 검사한다.

정상 complete committed-readback의 logical image acquisition 수는 각각 하나다. Capture open 자체가 실패한 early-return까지 marker 한 번을 강제하지는 않는다. 모든 실패 경로에서 Capture/marker를 두 번째 읽어 좋은 image를 찾는 동작은 금지한다. pending 검증·marker 생성은 별도 phase counter로 기록하고 그 앞선 bytes로 committed-readback을 생략하지 않는다.

receipt는 private constructor와 read-only accessor를 가진 immutable 결과로 설계한다. nullable immutable 결과 반환 또는 동등한 success-only publication을 사용한다. 과거 성공 A receipt가 있는 상태에서 B 호출이 실패했을 때 B의 결과가 미발행이어야 한다. mutable `OutReceipt`를 사용한다면 실패 때 이전 A를 새 성공으로 반환하는 일이 없도록 해당 호출의 output 상태를 직접 검사한다. bytes buffer 또는 descriptor를 보유할 수 있지만 descriptor는 검증한 **그 image**에서 계산되어야 한다.

기존 `ReadCommittedAndValidateExact`, `ReadAndValidateExact`, `HasValidCommittedMarker`의 signature와 호출자는 보존한다. collection Reader에서 이 path API를 연쇄 호출하지 않는다. Python 대조는 기존 `decode_committed_capture_bytes`를 사용하며 새 parser/CLI를 만들지 않는다.

P12는 실제 native sharing으로 차단된 swap과 dev seam으로 공급한 A/B/mixed/invalid image를 분리한다. native 보장을 약화시켜 race를 강제로 만들지 않는다. 실제 교체가 OS에서 거부되었으면 그 거부와 A image 성공을 기록한다. 다른 physical file로 rebound되었음을 감지했으면 최종 bytes가 A와 같아도 receipt를 발행하지 않는다. path가 바뀌지 않았다는 이유만으로 A/B ABA를 놓치지 않는다.

## 11. 실제 Commit 순서와 counter의 의미

- **D22**: collection intent 실패에는 legacy fallback 금지다. actual Coordinator의 final promotion/private start 뒤 marker→receipt→verified 순서를 유지한다.
- **D23**: producer verified와 collection accepted를 구분한다. metadata/group/context join·sidecar·diagnostic은 Task2E다.

| 순서 | 책임 | 실패·성공 oracle |
|---|---|---|
| Request | Host | same Snapshot/token/identity |
| pending+exact readback | additive Dataset/Store | precommit failure: Commit/start delta 0 |
| actual Coordinator(final promotion/private start) | Coordinator/Host | stale/promotion/start reject: verified delta 0 |
| marker | additive Dataset/Store | post-start failure: start 사실·raw final 보존 |
| receipt | additive Reader | same-image+current lease; failure unpublished |
| verified | Host | SlotHistory/VerifiedCaptureDecisionIds; accepted는 2E |

Request 앞의 Populate→Finalize→policy와 Record Build 앞의 고정 metadata 의미는 상위 Host 계약을 따른다. lower가 성공해도 actual Coordinator가 stale Request/Goal/target을 거부할 수 있다. `AtomicReserveAndStart`가 final promotion을 성공시킨 뒤에만 private start를 시도한다. marker는 actual start 뒤에 발행한다.

`DecisionCaptureWriteSuccessCount`는 기존 pending write 성공 의미를 유지한다. pending exact readback 실패 뒤 이 과거 write 사실을 지우지 않는다. `VerifiedCaptureDecisionIds`/SlotHistory의 producer verified는 committed receipt가 성공한 뒤다. Task2E의 sidecar exact readback 뒤 accepted와 분리한다. lower 시험에서 Host counter를 관찰하지 않았으면 해당 counter 0으로 보고하지 않는다.

storage failure는 Host에서 terminal/revoke/session block에 연결한다. callback·실패 통지 전에 latch와 exact lease를 닫고 local authority/context/owner pin을 유지한다. callback 뒤에는 같은 기존 binding을 재검사한다. committed-start stack 안의 동기 teardown/reset/reattach 금지와 stop-only 규칙을 보존한다. 실제 Executor drain·입력 정지/reset은 Task3다.

P06에서 junction 생성 권한 부족·지원 API 부재는 해당 행동 PASS가 아니다. 실제 ancestor rename/replace가 root **위** 경로와 목적지 parent 모두에서 차단됐는지 본다. root 내부 임의 악성 writer까지 방어했다는 결론은 제외한다.

P07 fault는 성공 control이 해당 stage까지 도달한 뒤 한 곳씩 주입한다. cleanup 전에 다른 identity가 같은 이름을 차지하는 경우, open 실패로 소유권이 생기지 않은 경우, marker 충돌 뒤 cleanup도 각각 확인한다. P10의 residual을 삭제한 뒤 markerless reject라고 보고하면 검사가 진공이다.

P12/P13은 bit flip만으로 끝내지 않는다. 정상 B envelope+marker-B, A Capture+marker-B, invalid-first→valid, A→B→A identity ABA를 포함한다. 실제 native read helper 계측과 image-validation seam의 역할을 분리하며 bytes parser를 시험용으로 복제하지 않는다. 혼합 image가 exact expected 검사에서 실패했는지 실제 assertion을 기록한다.
