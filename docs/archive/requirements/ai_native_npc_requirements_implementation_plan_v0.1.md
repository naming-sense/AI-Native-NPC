# AI Native NPC 의사결정 시스템
## 구체 요구사항 및 구현 계획서

- 문서 버전: v0.1
- 문서 목적: 전통적인 조건문 및 대규모 Behavior Tree 없이, NPC가 거리·시야·소리·관계·성격·기억을 바탕으로 행동을 판단하는 학습 기반 시스템의 요구사항과 구현 계획 정의
- 목표 독자: 게임 디자이너, AI/ML 엔지니어, 게임플레이 프로그래머, 테크니컬 디자이너, QA
- 권장 개발 전략: **행동 실행은 코드로 구현하고, 상황별 행동 판단은 학습 모델이 담당하는 하이브리드 구조**

---

# 1. 프로젝트 배경

전통적인 NPC AI는 일반적으로 다음 방식으로 구현된다.

- 특정 영역에 플레이어가 진입하면 플레이어를 감지한다.
- 플레이어가 시야 안에 있으면 바라본다.
- 뒤쪽에서 소리가 나면 뒤를 돌아본다.
- 관계가 적대적이고 무기를 들고 있으면 경고한다.
- 경고 이후에도 플레이어가 접근하면 공격한다.
- 체력이 낮거나 적의 수가 많으면 도망간다.

이 방식은 각 기능 자체는 단순하지만, 다음 변수들이 조합되면서 구현 복잡도가 급격히 증가한다.

- 거리
- 상대 방향
- 시야와 가림
- 소리 크기와 종류
- 최근 관측 시간
- 현재 행동
- NPC 역할
- 성격
- 플레이어와의 관계
- 체력과 자원
- 주변 아군과 적군
- 퀘스트 상태
- 장소와 시간
- 이전 대화와 사건

전통적인 조건문이나 Behavior Tree만으로 이를 구현하면 상황 조합마다 분기와 예외 처리가 필요하다. 프로젝트 규모가 커질수록 행동 트리가 비대해지고, NPC 유형별 로직이 중복되며, 새로운 입력 변수를 추가할 때 기존 로직 전체를 다시 검토해야 한다.

본 프로젝트는 다음과 같은 방식으로 문제를 전환한다.

> 개발자는 “뒤에서 소리가 나면 돌아본다” 같은 상황별 규칙을 작성하지 않는다.  
> 개발자는 NPC가 수행할 수 있는 행동 Skill, 감각 정보, 안전 제약, 캐릭터 원칙만 정의한다.  
> 학습 모델은 현재 상황에서 어떤 행동과 대상을 선택할지 판단한다.

# 2. 프로젝트 목표

## 2.1 핵심 목표

1. 상황별 조건문과 Behavior Tree 분기 작성량을 크게 줄인다.
2. 하나의 공용 의사결정 모델을 여러 NPC 역할과 성격에 재사용한다.
3. 새로운 상황 조합에서도 학습된 일반화를 통해 적절한 행동을 선택한다.
4. 디자이너가 코드 대신 캐릭터 원칙, 성격, 역할, 선호도 데이터를 통해 NPC를 제작할 수 있게 한다.
5. 실제 게임 런타임에서 안정적이고 예측 가능한 속도로 동작하게 한다.
6. 모델의 이상 행동을 탐지하고 재학습할 수 있는 데이터 파이프라인을 구축한다.
7. 필요 시 LLM을 개발 단계의 교사 또는 런타임 대사 생성기로 활용하되, 핵심 게임 상태 변경 권한은 부여하지 않는다.

## 2.2 비목표

초기 버전에서 다음 항목은 목표로 하지 않는다.

- 신경망이 직접 애니메이션 프레임을 생성하는 것
- 신경망이 매 프레임 이동 벡터를 직접 출력하는 것
- 신경망이 NavMesh 경로를 직접 계산하는 것
- LLM이 게임 상태를 직접 변경하는 것
- 모든 퀘스트 로직을 신경망에 맡기는 것
- 완전 자율적인 장기 서사 생성
- 학습 없이 즉시 모든 NPC 행동을 자동 생성하는 것
- 물리적으로 불가능한 행동이나 퀘스트 금지 행동을 모델 판단에만 맡기는 것

# 3. 핵심 설계 원칙

## 3.1 판단과 실행의 분리

시스템은 크게 두 부분으로 나뉜다.

### 학습 모델이 담당하는 영역

- 현재 상황의 의미 해석
- 관심 대상 선택
- 고수준 행동 의도 선택
- 행동 강도 선택
- 행동 지속 시간 제안
- 경계, 공포, 분노, 호기심 등 단기 감정 변화 제안
- 플레이어와의 관계 변화 제안
- 여러 후보 행동의 적합도 평가

### 게임 코드가 담당하는 영역

- 시야, 거리, 소리 등 감각 데이터 계산
- NavMesh 이동
- 회전 및 LookAt
- 애니메이션 실행
- 공격 판정
- 대화 재생
- 행동 성공 및 실패 조건
- 쿨다운
- 물리적 가능 여부
- 퀘스트 및 서사상 금지 조건
- 세이브 및 로드
- 네트워크 동기화
- 치트 방지 및 권한 검증

## 3.2 행동 규칙이 아닌 행동 원자 구현

개발자가 구현해야 할 것은 다음과 같은 재사용 가능한 행동 Skill이다.

- `Idle`
- `ContinueCurrentAction`
- `LookAt`
- `TurnTo`
- `Approach`
- `KeepDistance`
- `RetreatFrom`
- `Follow`
- `Investigate`
- `SearchArea`
- `Greet`
- `Warn`
- `AskQuestion`
- `CallForHelp`
- `TakeCover`
- `Flee`
- `Attack`
- `Interact`
- `UseItem`

각 Skill에는 상황별 판단 로직을 넣지 않는다.

잘못된 예:

```cpp
if (Sound.IsBehind() && Sound.Distance < 5.0f && Suspicion > 0.4f)
{
    TurnTo(Sound.Position);
}
```

권장 예:

```cpp
class TurnToSkill
{
public:
    bool CanExecute(const FTarget& Target) const;
    void Start(const FTarget& Target, const FActionParameters& Params);
    ESkillStatus Tick(float DeltaTime);
    void Cancel();
};
```

`TurnToSkill`은 지정된 대상을 자연스럽게 바라보는 기능만 제공한다. 현재 상황에서 이 행동을 선택할지는 학습 모델이 결정한다.

## 3.3 하드 제약과 소프트 판단의 분리

### 하드 제약

반드시 코드에서 보장해야 한다.

- 죽은 NPC는 행동할 수 없음
- 무기가 없으면 무기 공격 불가
- 공격 금지 퀘스트 상태에서는 플레이어 공격 불가
- 존재하지 않는 대상을 선택할 수 없음
- 이동할 수 없는 위치로 이동 불가
- 대화할 수 없는 상태에서 대화 불가
- 게임 규칙상 허용되지 않은 아이템 전달 불가

### 소프트 판단

학습 모델이 결정한다.

- 지금 공격하는 것이 적절한가
- 소리를 무시할 것인가 조사할 것인가
- 플레이어에게 먼저 경고할 것인가
- 공격 대신 후퇴할 것인가
- 누구를 가장 중요한 대상으로 볼 것인가
- 얼마나 오래 경계할 것인가

# 5. 기능 요구사항

## 5.1 감각 입력 시스템

### FR-SENSOR-001 거리 입력

시스템은 NPC와 대상 간 거리를 정규화된 값으로 제공해야 한다.

권장 입력:

- 실제 거리
- 최대 감지 거리로 나눈 정규화 거리
- 로그 거리
- 상대 위치 X/Y/Z
- 접근 또는 이탈 속도
- 최근 최소 거리
- 최근 평균 거리

### FR-SENSOR-002 방향 입력

각도는 단일 각도값보다 다음 방식으로 제공한다.

- 상대 방향의 `sin`
- 상대 방향의 `cos`
- NPC 정면 기준 좌우 값
- NPC 정면 기준 앞뒤 값
- 수직 방향 차이
- 시야 중심으로부터의 편차

### FR-SENSOR-003 시야 입력

각 대상에 대해 다음 값을 제공해야 한다.

- 현재 보이는지 여부
- 부분적으로 보이는 정도
- 가려짐 비율
- 마지막으로 본 이후 경과 시간
- 마지막으로 본 위치
- 시야 신뢰도
- 시야 내 머문 시간

### FR-SENSOR-004 소리 입력

소리 이벤트는 다음 정보를 포함해야 한다.

- 소리 종류
- 소리 크기
- NPC 기준 상대 방향
- 발생 위치
- 발생 후 경과 시간
- 반복 횟수
- 추정 원인
- 원인 개체 ID
- 신뢰도
- 위험도 힌트

소리 종류 예시:

- 발소리
- 달리기
- 총성
- 폭발
- 문 열림
- 물건 낙하
- 대화
- 비명
- 구조 요청
- 기계 소음

### FR-SENSOR-005 입력 유효성

각 센서 값에는 필요 시 다음 메타데이터를 포함해야 한다.

- `valid`
- `confidence`
- `age`
- `source`
- `is_inferred`

값이 0인 것과 관측되지 않은 것을 구분해야 한다.

## 5.2 NPC 상태 입력

### FR-NPC-001 자기 상태

- 체력
- 스태미나
- 탄약
- 사용 가능한 아이템
- 이동 가능 여부
- 현재 행동
- 현재 행동 지속 시간
- 이전 행동
- 최근 행동 실패 횟수
- 피격 여부
- 최근 피해량
- 엄폐 여부
- 현재 임무
- 현재 구역
- 전투 허용 상태

### FR-NPC-002 성격

NPC 성격은 연속형 벡터로 표현한다.

권장 항목:

- 공격성
- 용기
- 호기심
- 충성심
- 사교성
- 충동성
- 인내심
- 경계심
- 이타성
- 규칙 준수 성향

모든 값은 `[-1, 1]` 또는 `[0, 1]` 범위로 정규화한다.

### FR-NPC-003 역할

역할은 Embedding 또는 범주형 ID로 제공한다.

예시:

- 경비병
- 민간인
- 상인
- 동료
- 적군 병사
- 지휘관
- 의료인
- 도둑
- 야생동물
- 몬스터

### FR-NPC-004 단기 감정

다음 감정 상태를 명시적으로 관리한다.

- 공포
- 분노
- 의심
- 호기심
- 긴장
- 친밀감
- 당황
- 자신감

감정은 시간에 따라 감쇠할 수 있어야 한다.

## 5.3 관계 시스템

### FR-REL-001 다축 관계 표현

플레이어와 NPC 관계를 단일 우호도 값으로 표현하지 않는다.

권장 관계 벡터:

- 호감
- 신뢰
- 존중
- 두려움
- 빚
- 의심
- 충성
- 적대감

### FR-REL-002 장기 관계와 단기 감정 분리

- 신뢰, 존중, 빚 등은 장기 상태로 관리한다.
- 공포, 분노, 의심 등은 단기 상태로 관리한다.
- 장기 관계 값은 중요한 사건과 스크립트에 의해 직접 보정 가능해야 한다.
- 모델이 제안한 관계 변화량은 허용 범위 내에서만 반영해야 한다.

### FR-REL-003 관계 변경 로그

모든 관계 변화는 다음 정보를 기록해야 한다.

- 변경 전 값
- 변경 후 값
- 변경 원인
- 모델 제안값
- 규칙 또는 퀘스트 보정값
- 발생 시간
- 관련 개체
- 관련 사건 ID

---

## 5.4 명시적 기억 시스템

### FR-MEM-001 단기 기억

GRU 또는 유사 순환 상태가 담당한다.

사용 예:

- 몇 초 전 뒤에서 소리가 났음
- 플레이어가 방금 무기를 꺼냈음
- NPC가 방금 경고했음
- 플레이어가 경고를 무시했음

### FR-MEM-002 장기 기억

세이브 가능한 구조화 데이터로 관리한다.

예시:

- 플레이어가 NPC를 치료함
- 플레이어가 NPC의 물건을 훔침
- 플레이어가 약속을 지킴
- 플레이어가 제한 구역에 반복 침입함
- 플레이어가 NPC 동료를 공격함

### FR-MEM-003 기억 검색

현재 판단에 관련성이 높은 기억만 입력으로 제공한다.

기억 검색 기준:

- 대상 동일성
- 사건 유형
- 발생 시간
- 감정 강도
- 현재 목표와 관련성
- 장소 관련성

초기 버전에서는 임베딩 검색보다 규칙 기반 Top-K 검색을 사용해도 된다.

## 5.5 주변 개체 표현

### FR-ENTITY-001 가변 개체 수 처리

주변 개체 수가 변하므로 고정 순서 벡터 연결만 사용하지 않는다.

권장 방식:

- 각 개체를 공통 Entity Encoder로 인코딩
- Attention Pooling 또는 Set Encoder 사용
- 최대 개체 수 제한
- 중요도 기반 후보 선정

### FR-ENTITY-002 개체 입력

각 개체별 입력 예시:

- 개체 종류
- 상대 위치
- 거리
- 방향
- 가시성
- 마지막 관측 시간
- 위협 수준
- 관계
- 현재 행동
- 무기 상태
- 체력 추정
- 목표 여부
- 상호작용 가능 여부

# 8. 신경망 아키텍처

## 8.1 권장 모델: Neural Action Scorer

모델은 상황 전체를 입력받아 행동 클래스 하나를 바로 출력하기보다, 각 후보 행동의 적합도 점수를 계산한다.

```text
Score = f(State, CandidateAction, CandidateTarget, Memory, Personality)
```

이 구조의 장점:

- 행동과 대상 조합을 유연하게 평가 가능
- 새로운 대상 추가가 쉬움
- 동일 행동을 다양한 대상에 재사용 가능
- 후보 생성과 하드 제약을 엔진에서 제어 가능
- 디버깅 시 후보별 점수 확인 가능
- 새로운 Skill 추가 시 전체 출력 Head를 크게 변경하지 않아도 됨

## 8.2 입력 인코더

### Context Encoder

입력:

- NPC 자기 상태
- 역할
- 성격
- 감정
- 관계
- 현재 목표
- 환경 정보

권장 구조:

```text
Input 64~128
Linear → 128
SiLU
LayerNorm
Linear → 128
```

### Entity Encoder

입력:

- 개체별 특징 24~48차원

권장 구조:

```text
Input 24~48
Linear → 64
SiLU
Linear → 64
LayerNorm
```

### Entity Aggregator

V1 선택지:

- Attention Pooling
- Set Transformer
- 단순 Max/Mean Pooling과 Attention 결합

권장 V1:

```text
Entity Embedding 64
Multi-Head Attention 2~4 heads
Output Context 128
```

### Memory Encoder

권장 V1:

```text
GRU
Input 256
Hidden 128
```

입력:

- Context Encoder 출력
- Entity Aggregator 출력
- 이전 행동 Embedding
- 이전 결과 Embedding

### Action Encoder

입력:

- Skill ID
- 행동 카테고리
- 이동/대화/공격 여부
- 기본 지속 시간
- 위험도
- 현재 행동과 동일한지 여부

권장 구조:

```text
Skill Embedding 32
Metadata MLP 16
Concat → 48
Linear → 64
```

### Target Encoder

대상 개체의 Entity Embedding을 재사용한다.

대상이 없는 경우 학습 가능한 `NoTarget Embedding`을 사용한다.

## 8.3 Score Head

```text
GRU Hidden 128
Action Embedding 64
Target Embedding 64
Additional Pair Features 32
Concat 288
Linear → 128
SiLU
Linear → 64
SiLU
Linear → 1
```

출력:

- 후보 행동 적합도 점수

선택적으로 다음 Head를 추가한다.

- 행동 지속 시간
- 행동 강도
- 선호 거리
- 대화 톤
- 감정 변화량
- 관계 변화량
- 판단 확신도
- 상태 가치

## 8.4 초기 모델 크기

권장 목표:

- 파라미터 수: 약 0.5M~3M
- CPU 추론 가능
- 다수 NPC 배치 추론 지원
- FP16 또는 INT8 양자화 가능
- NPC당 매 프레임 추론하지 않음

# 9. 의사결정 안정화

## 9.1 판단 주기

권장 V1:

- 일반 판단: 초당 2~5회
- 비전투 저우선 NPC: 초당 1~2회
- 전투 NPC: 초당 5~10회
- 이동 및 애니메이션: 매 프레임
- 피격, 폭발, 근접 위협: 이벤트 기반 즉시 재평가

## 9.2 행동 전환 비용

새 행동 선택 시 다음 값을 점수에서 차감한다.

- 현재 행동 취소 비용
- 애니메이션 전환 비용
- 목표 변경 비용
- 최근 반복 행동 패널티
- 실패한 행동 재시도 패널티

## 9.3 최소 행동 지속 시간

각 Skill에 최소 지속 시간을 둔다.

예시:

- `LookAt`: 0.5초
- `Warn`: 1.5초
- `Investigate`: 3초
- `SearchArea`: 5초
- `Flee`: 2초

## 9.4 긴급 인터럽트

다음 사건은 최소 지속 시간 중에도 재평가를 허용한다.

- 피격
- 폭발
- 대상 사망
- 목표 소실
- 경로 차단
- 플레이어의 급격한 접근
- 퀘스트 상태 변경
- 중요 대화 이벤트
- 네트워크 권한 변경

## 9.5 확신도 기반 Fallback

모델 확신도가 낮거나 후보 점수 차이가 작으면 다음 중 하나를 사용한다.

- 현재 행동 유지
- 안전한 기본 행동
- 디자이너 지정 fallback
- 규칙 기반 최소 안전 정책

# 11. LLM 교사 데이터 생성

## 11.1 LLM의 역할

LLM은 런타임 핵심 판단 모델이 아니라 개발 단계에서 행동 후보를 평가하는 교사로 사용한다.

입력:

- NPC 역할 설명
- 성격
- 관계
- 현재 상황
- 최근 사건
- 가능한 행동 후보
- 절대 금지 조건

출력:

- 후보 행동 순위
- 후보별 점수
- 선택 이유 요약
- 비정상 후보 표시
- 모호성 여부

## 11.2 캐릭터 원칙 예시

```text
이 NPC는 제한 구역을 지키는 경비병이다.

- 불확실한 소리는 먼저 확인한다.
- 명백한 위협이 아니면 공격 전에 경고한다.
- 혼자이고 겁이 많으면 지원을 요청한다.
- 신뢰하는 인물에게는 덜 공격적으로 반응한다.
- 반복적으로 규칙을 어기는 인물에게는 경고 단계를 줄인다.
- 민간인에게 불필요한 폭력을 사용하지 않는다.
```

## 11.3 후보 평가 형식

권장 출력:

```json
{
  "ranking": [
    {
      "candidate_id": 4,
      "score": 0.91
    },
    {
      "candidate_id": 2,
      "score": 0.67
    }
  ],
  "ambiguous": false,
  "unsafe_candidates": [7]
}
```

## 11.4 LLM 데이터 품질 관리

- 동일 상황을 여러 프롬프트 변형으로 평가
- 복수 모델 또는 복수 샘플 합의
- 자기 일관성 검사
- 하드 제약 위반 자동 제거
- 행동 원칙과 결과의 모순 검사
- 무작위 샘플 사람 검수
- 특정 행동 편향 검사
- 역할별 행동 분포 검사

- 여러 행동이 모두 가능함 표시

## 12.2 선호 비교 도구

두 행동 또는 두 시퀀스를 비교한다.

질문 예:

- 어느 쪽이 더 자연스러운가
- 어느 쪽이 캐릭터 성격에 맞는가
- 어느 쪽이 게임플레이적으로 더 재미있는가
- 어느 쪽이 더 안전하고 이해 가능한가

출력:

- A 선호
- B 선호
- 동등
- 둘 다 부적절
- 판단 불가

## 12.3 Active Learning

사람 검수는 모든 데이터가 아니라 다음 샘플에 집중한다.

- 1위와 2위 점수 차이가 작은 상황
- 모델 확신도가 낮은 상황
- 실제 플레이에서 이상 행동이 발생한 상황
- 새로운 Skill이 포함된 상황
- 새로운 NPC 역할
- 희귀 퀘스트 상태
- 모델과 LLM 교사가 크게 불일치한 상황

# 13. 학습 방식

## 13.1 1단계: 행동 순위 학습

권장 손실:

- Pairwise Ranking Loss
- Listwise Ranking Loss
- 후보별 회귀 손실
- 행동 클래스 보조 분류 손실

예시:

```text
좋은 행동 점수 > 나쁜 행동 점수
```

모델이 단일 정답만 외우지 않고, 여러 적절한 행동 간 상대적 선호를 학습하도록 한다.

## 13.2 2단계: 시퀀스 모방학습

GRU 학습을 위해 연속된 trajectory를 사용한다.

권장:

- Sequence Length: 16~64 decision steps
- Burn-in: 4~16 steps
- Episode 경계에서 hidden state 초기화
- 실패와 행동 전환 로그 포함
- 이전 행동과 결과를 다음 입력에 포함

## 13.3 3단계: 보조 과제

선택적 보조 Head:

- 다음 순간 플레이어 가시성
- 다음 위협 수준
- 소리 원인 종류
- 현재 행동 성공 가능성
- 대상 이탈 가능성
- 긴급 인터럽트 발생 가능성
- 다음 감정 상태

## 13.4 4단계: 강화학습 미세조정

PPO 등은 기본 상식 학습 이후에만 적용한다.

적용 대상:

- 탐색 효율
- 거리 조절
- 협동
- 생존
- 엄폐 선택
- 행동 타이밍
- 장기적인 임무 수행

주의:

- 자연스러움 자체를 단순 보상으로 정의하지 않는다.
- 보상 해킹 탐지 장치를 마련한다.
- 안전 정책과 행동 Mask를 유지한다.
- 학습 모델과 출시 모델을 분리한다.
- 자동 회귀 테스트를 통과한 모델만 배포한다.

# 14. 런타임 추론 시스템

## 14.1 추론 요청

NPC는 다음 상황에서 추론을 요청한다.

- 정기 판단 주기 도달
- 현재 행동 종료
- 현재 행동 실패
- 중요 센서 이벤트
- 새로운 위협 등장
- 관계 또는 퀘스트 상태 변경
- 대상 소실
- 긴급 인터럽트

## 14.2 배치 추론

여러 NPC 요청을 프레임 단위 또는 짧은 시간 창으로 묶는다.

권장:

- 2~10ms 요청 수집 창
- 우선순위 기반 큐
- 화면 밖 NPC는 낮은 빈도
- 중요 NPC는 높은 빈도
- 전투 NPC 우선
- 동일 모델을 사용하는 NPC 배치 추론

## 14.3 성능 목표 예시

V1 목표 예시:

- 동시 활성 NPC: 50
- 실제 추론 NPC: 프레임당 5~20
- NPC당 후보: 최대 32
- 평균 추론 지연: 2ms 이하 목표
- 최악 지연: 8ms 이하 목표
- 메모리: NPC별 hidden state 1KB 이하 목표
- 모델 크기: 10MB 이하 목표

실제 목표는 대상 플랫폼에 맞게 조정한다.

## 17.2 시나리오 테스트

필수 시나리오 예시:

1. 뒤에서 작은 발소리가 발생함
2. 뒤에서 큰 총성이 발생함
3. 플레이어가 무기를 꺼냈다가 넣음
4. 우호적인 플레이어가 제한 구역에 진입함
5. 적대적 플레이어가 멀리서 관찰함
6. NPC가 혼자인 상태에서 다수 적을 발견함
7. 겁이 많은 NPC와 용감한 NPC 비교
8. 플레이어가 경고를 반복적으로 무시함
9. 플레이어가 NPC를 치료한 직후 접근함
10. 대상이 시야에서 사라짐
11. 소리가 여러 방향에서 동시에 발생함
12. 행동 실행 중 경로가 막힘
13. 공격 도중 퀘스트 상태가 변경됨
14. 모델 확신도가 낮음
15. 추론 시스템이 실패함

## 17.3 회귀 테스트

모델 버전마다 고정된 시나리오 세트를 실행한다.

- 반응 시간
- 공격 비율
- 도망 비율
- 경고 후 공격 비율
- 금지 행동 발생 여부
- 캐릭터별 행동 일관성

## 17.4 모델 안전 테스트

- Mask된 행동 선택 여부
- 존재하지 않는 대상 선택 여부
- 퀘스트 금지 행동 시도 여부
- 반복 루프
- 무한 회전
- 행동 진동
- 항상 공격
- 항상 도망
- 대사 반복
- 플레이어 추적 집착
- 무관한 소리에 과반응

# 21. 실패 대응 및 Fallback

## 21.1 추론 실패

추론 런타임 오류 시:

1. 현재 안전한 행동 유지
2. 기본 행동 정책 사용
3. 중요 NPC는 간단한 fallback 정책 실행
4. 오류 로그 기록
5. 일정 시간 후 재시도

## 21.2 잘못된 출력

- NaN 또는 Inf 점수 제거
- 모든 후보가 Mask된 경우 Idle 또는 안전 행동
- 존재하지 않는 대상 무효화
- 파라미터 범위 Clamp
- 관계 및 감정 변화량 Clamp

## 21.3 최소 안전 정책

최소 안전 정책은 완전한 Behavior Tree가 아니라 시스템 보호용이다.

예시:

- 피격 중이고 공격 불가하면 엄폐 또는 도망
- 경로 없음이면 이동 취소
- 대상 없음이면 현재 행동 유지
- 모든 후보 무효면 Idle
- 치명적 위험이면 긴급 회피

- 하드 제약 위반 0건
- 기본 상황에서 Top-3 적절 행동 포함률 90% 이상 목표
- 행동 진동 평균 기준 충족
- 성격이 다른 NPC 간 행동 차이가 관찰됨
- 새로운 역할 프리셋을 코드 수정 없이 추가 가능
- 전통적인 분기 로직 없이 “뒤쪽 소리 → 확인 행동”이 일반화됨

# 27. 핵심 결론

이 프로젝트의 목적은 Behavior Tree를 신경망으로 그대로 복제하는 것이 아니다.

핵심은 다음 전환이다.

```text
상황별 반응을 코드로 작성
        ↓
행동 Skill과 안전 제약만 코드로 작성
        ↓
상황과 후보 행동의 적합도를 데이터로 학습
```

개발자가 정의할 대상은 다음과 같다.

- NPC가 무엇을 할 수 있는가
- 무엇이 물리적 또는 서사적으로 금지되는가
- 이 NPC는 어떤 역할과 성격을 가지는가
- 좋은 행동의 기준은 무엇인가

학습 시스템이 담당할 대상은 다음과 같다.

- 현재 상황에서 무엇이 중요한가
- 누구를 대상으로 행동해야 하는가
- 어떤 행동이 가장 자연스러운가
- 언제 행동을 바꿔야 하는가
- 관계와 기억을 현재 판단에 어떻게 반영할 것인가

이 구조가 안정적으로 완성되면, NPC 종류와 상황 수가 증가할수록 전통적인 상황별 분기 방식보다 재사용성과 확장성에서 더 큰 이점을 얻을 수 있다.
